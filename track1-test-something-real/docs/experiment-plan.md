# Experiment contract — draft before evaluation traffic

Status: local implementation; no live Flagsmith results collected. Freeze this document and the answer key before evaluation traffic. Local automated checks are development verification, not the final experiment.

## Question

Does a ranked and explained decision brief help first-time finance operators record a correct action on a priority account, compared with a conventional invoice register?

Hypothesis: showing the decision brief increases the share of operators completing a valid priority-account task within 10 minutes, from an assumed 35% to 45% (+10 percentage points), during a 48-hour evaluation. Those rates are planning assumptions, not observed baselines.

- Eligible: new anonymous operators with the fixed sample portfolio and a displayed workspace.
- Flag: `collections_workspace`. Control default value/key `control`; treatment value/key `decision_brief`.
- Allocation: 100% of eligible identities, 50:50. No targeting overrides.
- A: invoice register in ID order, filters, and standard portfolio metrics.
- B: same dataset and tools, ranked queue plus top-three brief and visible reason lines.
- Controlled: same API, rank/model calculation, task dialog, validation, scenario access, and assets.
- Exposure: separate backend call after workspace renders; first server timestamp persists.
- Primary: `valid_collection_action`, occurrence, increase. Numeric value = seconds from first exposure.
- Valid: existing invoice, correct action for status/date, non-empty human review note, account in the fixed top-five priority set, <=600 seconds from first exposure.
- Each operator converts once. Task retries cannot create multiple tasks for the same invoice.
- Guardrails: `low_priority_action` occurrence, decrease; `invalid_action_attempted` occurrence, decrease; mean primary-event seconds, decrease. Occurrence is deliberate: fraction of operators affected, not raw attempt count.
- Actions outside the priority set can still be legitimate work and are saved; they do not count as the priority-task conversion.

## Fixed answer key

Generated by aggregating per-invoice `value_per_hour` by customer on the unchanged sample dataset before task outcomes. The implementation derives this deterministically from `backend/quant.py` assumptions and `backend/main.py` sample invoices; source and data must be frozen before the experiment. Changing ranking assumptions or the portfolio requires a new experiment.

This is a task benchmark under published business assumptions, not an objective truth about real-world credit risk. The treatment displays the same rank model used to define the benchmark; the experiment measures navigation and task execution against that benchmark. Actual cash recovery needs a different longitudinal study.

## Cohorts and data integrity

Human and synthetic traffic belong in separate Flagsmith environments/databases, even though the Lab also separates local cohorts. Metadata contains `simulated`, `run_id`, and `source`. Forced previews and fallback sessions never enter the measured cohort. Imports are blocked for enrolled live sessions and excluded from local statistics.

The local demo's hash assignment is for preview only. Live enrollment must come from Flagsmith, including an enabled flag, matching variation key, and `in_experiment` state. Missing key/network/flag errors use a non-enrolled control fallback.

## Evidence and decision

Collect exposures/conversions per arm, observed allocation, excluded identities, computation time, probability of beating control, lift interval, guardrail effects, and traffic provenance directly from Flagsmith. Wait at least 10 minutes after the last first exposure before final cohort reporting.

Do not recommend rollout unless evidence is complete, each arm has >=50 identities and >=5 conversions, win probability >95%, the lift interval is above zero, SRM is absent, excluded identities have been investigated, and guardrails pass. A minimum floor alone is not adequate precision. Define acceptable guardrail degradation before the real run; until that is signed off, keep `guardrail_passed` null.

`review_decision.py` conservatively blocks any nonzero excluded count. It reviews manually transcribed evidence, not authenticated results; a human must verify the evidence against the dashboard. It never mutates an experiment.

## A/A and simulation

Run an actual A/A with identical rendered experiences in a separate environment/flag before A/B; do not claim this has already happened. The simulator's `null` model only gives both arms equal scripted conversion probabilities and does not make the two UIs identical.

Synthetic model: 30% conversion in both arms for `null`, 30%/38% for `effect`. Default wait is zero. This proves instrumentation and fail-closed decisions under assumptions, not human efficiency. Browser tests demonstrate working paths but likewise do not establish product impact.
